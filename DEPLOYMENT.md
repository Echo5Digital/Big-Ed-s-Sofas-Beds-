# Deployment Guide — Vercel + Render

Target topology:

```
apps/storefront  →  Vercel project #1  (public e-commerce site)
apps/admin       →  Vercel project #2  (staff dashboard)
apps/api         →  Render web service (Express API)
Postgres         →  Render managed database
```

`apps/pos` is not deployed anywhere yet — it's an intentional placeholder (see `apps/pos/README.md`).

The storefront currently runs entirely on local mock data (`apps/storefront/lib/mock-data/`) and does not call the API yet, so it has no environment variables to configure for this pass — it deploys as a standalone static/SSR Next.js app with zero backend dependency. Only `apps/admin` and `apps/api` talk to each other.

---

## 0. Before you start: generate the first Prisma migration

No migration files exist in this repo yet (`packages/database/prisma/migrations/` doesn't exist) because this sandbox has no live Postgres to generate them against. **Do this once, locally, before deploying the API:**

1. Get a Postgres connection string — easiest is a free [Neon](https://neon.tech) or [Supabase](https://supabase.com) project (no local install needed), or use a local/Docker Postgres.
2. Edit `packages/database/.env` and set `DATABASE_URL` to that connection string.
3. Run:
   ```bash
   pnpm install
   cd packages/database
   pnpm migrate
   ```
   This creates `prisma/migrations/<timestamp>_init/` and applies it. **Commit that new folder to git** — Render's deploy step runs `prisma migrate deploy`, which only *applies* existing migration files, it never generates new ones.
4. Optionally seed that same database now: `pnpm seed` (prints a generated admin login — save it, you'll need it to sign into the admin app).

You can reuse this same database for Render (point Render's `DATABASE_URL` at it) or create a fresh one on Render and repeat step 3's `pnpm migrate` against that one instead — either works, just make sure the migration files are committed either way.

## 1. Render — Postgres + API

### Option A: Blueprint (one click, uses the committed `render.yaml`)

1. Push this repo to GitHub/GitLab.
2. In the Render dashboard: **New → Blueprint**, select this repo. Render reads `render.yaml` at the repo root and provisions both the database and the API service.
3. Render will prompt for the one `sync: false` variable: `CORS_ORIGINS`. Leave it blank for now — you'll fill it in after step 2 (Vercel) gives you real URLs.
4. `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` are auto-generated by Render (`generateValue: true`) — you never need to touch these.
5. Deploy. Watch the build logs — the build command runs `pnpm install`, `prisma generate`, and `prisma migrate deploy` (applying the migration you committed in step 0).

### Option B: Manual setup (no Blueprint)

1. **New → PostgreSQL** — name it, choose the free plan, create it. Copy its **Internal Connection String**.
2. **New → Web Service** — connect this repo.
   - Root Directory: leave as repo root (the build command `cd`s as needed).
   - Build Command:
     ```
     pnpm install --frozen-lockfile && pnpm --filter @big-eds/database generate && pnpm --filter @big-eds/database migrate:deploy
     ```
     (Don't add `corepack enable` — Render's filesystem is read-only where corepack tries to symlink the pnpm binary. Render's Node runtime already has pnpm available; pin the version via the `PNPM_VERSION` env var instead, see below.)
   - Start Command: `pnpm --filter @big-eds/api start`
   - Health Check Path: `/health`
3. Add environment variables (Render dashboard → your service → Environment):

   | Key | Value |
   |---|---|
   | `NODE_ENV` | `production` |
   | `PNPM_VERSION` | `9.15.0` |
   | `DATABASE_URL` | the Postgres Internal Connection String from step 1 |
   | `PORT` | `4000` |
   | `JWT_ACCESS_SECRET` | a long random string (`openssl rand -base64 48`) |
   | `JWT_REFRESH_SECRET` | a different long random string |
   | `ACCESS_TOKEN_TTL_MINUTES` | `15` |
   | `REFRESH_TOKEN_TTL_DAYS` | `7` |
   | `CORS_ORIGINS` | fill in after step 2 below |
   | `COOKIE_SECURE` | `true` |
   | `COOKIE_SAME_SITE` | `none` |

### After either option: note your API URL

Render gives you a URL like `https://big-eds-retail-os-api.onrender.com`. You'll need it for the admin app's env var in step 2, and the `/health` endpoint should return `{"status":"ok", ...}` once deployed — check that before moving on.

> **Free-plan note:** Render's free web services spin down after inactivity and take ~30–60s to wake on the next request. That's expected on the free tier, not a bug — upgrade the plan if that latency is a problem for your use case.

## 2. Vercel — Admin dashboard

1. In Vercel: **Add New → Project**, import this repo.
2. **Root Directory**: set to `apps/admin` (Vercel's project settings UI, under "Root Directory" — click Edit and select it). Vercel detects `pnpm-lock.yaml` at the repo root and automatically runs `pnpm install` from there (resolving the `workspace:*` dependencies correctly), then builds from `apps/admin`. Leave Build/Install/Output Command settings on their defaults — don't override them, and don't add a custom `installCommand` that skips the real install, or Vercel's framework-detection step will fail with "No Next.js version detected" even though `next` is a real dependency (it needs `node_modules` actually populated, not just listed in `package.json`).
3. Framework Preset: Next.js (auto-detected).
4. Environment Variables:

   | Key | Value |
   |---|---|
   | `NEXT_PUBLIC_API_URL` | your Render API URL from step 1, e.g. `https://big-eds-retail-os-api.onrender.com` (no trailing slash) |

5. Deploy. Vercel gives you a URL like `https://big-eds-admin.vercel.app`.
6. **Go back to Render** and set `CORS_ORIGINS` to include this exact URL (comma-separate if you also deploy the storefront and want it included too, though the storefront doesn't call the API yet):
   ```
   https://big-eds-admin.vercel.app
   ```
   Redeploy the Render service (or it may auto-restart on env var change, depending on your plan) for the new CORS origin to take effect.
7. Visit the admin URL, sign in with the seeded admin credentials from step 0.4. If login fails with a CORS or network error, double-check `NEXT_PUBLIC_API_URL` has no typo/trailing slash and `CORS_ORIGINS` on Render exactly matches the Vercel URL (scheme + host, nothing else).

## 3. Vercel — Storefront

1. **Add New → Project** again (a separate Vercel project from the admin one), import the same repo.
2. **Root Directory**: `apps/storefront`. Same note as the admin app above — leave Vercel's Build/Install/Output Command settings on their defaults.
3. Framework Preset: Next.js (auto-detected). No environment variables are required for this pass — the storefront doesn't call the API yet (see the note at the top of this doc).
4. Deploy. Vercel gives you a URL like `https://big-eds-storefront.vercel.app`.

## 4. Custom domains (when ready)

You mentioned a possible future setup with both apps under one parent domain via subdomains (e.g. `admin.bigeds.com` + `api.bigeds.com`). When you're ready:

1. Add the custom domains in each Vercel project's Domains settings, and in Render's service settings for the API.
2. Once both are live on real subdomains of the *same* parent domain, you can optionally switch cookie behavior back to `sameSite=lax` (slightly simpler/stricter) by setting `COOKIE_SAME_SITE=lax` on Render — `none` still works fine across subdomains too, so this is optional, not required.
3. Update `CORS_ORIGINS` on Render and `NEXT_PUBLIC_API_URL` on the admin Vercel project to the new custom domain URLs.

## Troubleshooting

- **Admin login succeeds but subsequent requests act logged-out**: almost always a cookie attribute mismatch. Confirm Render has `COOKIE_SECURE=true` and `COOKIE_SAME_SITE=none` (required for a different-domain Vercel↔Render setup — `None` cookies are rejected by browsers unless `Secure` is also set, which is why both must be true together).
- **CORS error in the browser console**: `CORS_ORIGINS` on Render must match the calling origin *exactly* — same scheme, same host, no path, no trailing slash. Check for `www.` mismatches too.
- **Render build fails on `prisma migrate deploy` with "No migration found"**: you skipped step 0 — generate and commit the initial migration locally first.
- **Vercel build fails with "command not found: pnpm"**: shouldn't happen (Vercel's Next.js framework preset handles pnpm automatically when it detects `pnpm-lock.yaml` at the repo root), but if it does, check that `packageManager` in the root `package.json` is still set correctly.
- **Vercel build fails with "No Next.js version detected"**: this means something is overriding the Install Command (in the dashboard or in `vercel.json`) in a way that skips the real `pnpm install` — Vercel's framework-detection step needs `next` actually present in `node_modules`, not just listed in `package.json`. Fix: don't set a custom Install/Build Command in the Vercel project settings, and keep `apps/storefront/vercel.json` / `apps/admin/vercel.json` to just `{"framework": "nextjs"}` — let Vercel's native pnpm-workspace detection (triggered by finding `pnpm-lock.yaml` at the repo root) handle the install.
- **Render build fails with `EROFS: read-only file system, unlink '/usr/bin/pnpm'`**: caused by running `corepack enable` on Render — its build filesystem has `/usr/bin` mounted read-only, so corepack can't symlink the pnpm binary there. Render's Node runtime already ships with pnpm; don't call `corepack enable`/`corepack prepare` at all — just set a `PNPM_VERSION` environment variable (e.g. `9.15.0`) to pin the version, which `render.yaml` already does.
